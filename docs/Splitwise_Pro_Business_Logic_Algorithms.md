# Business Logic & Algorithms — Splitwise Pro

**Version:** 1.0  
**Status:** MVP Financial Logic Specification  
**Currency:** INR  
**Money representation:** Whole rupees / integers

---

# 1. Purpose

This document defines the authoritative financial rules and deterministic algorithms used by Splitwise Pro.

It covers:

- Expense balance calculation
- Equal and unequal splitting
- Split rounding
- Person removal
- Balance recalculation
- Settlement effects
- Smart Settlement
- Expense editing/deletion
- Categories
- Concurrency considerations
- Financial edge cases

The backend is the source of truth for all financial calculations.

---

# 2. Core Financial Model

Every person's balance represents their current net financial position within the group.

```text
Positive balance = person should receive money
Negative balance = person should pay money
Zero balance     = person is settled
```

Example:

```text
Sidhant   +₹670
Rahul     -₹420
Arjun     -₹250
```

The balances must always satisfy:

```text
sum(all current balances) = 0
```

---

# 3. Expense Balance Formula

For every expense:

1. Add the full expense amount to the payer.
2. Subtract each participant's share from that participant.

Formula:

```text
balance[payer] += expense.amount

for each share:
    balance[person] -= share.amount
```

The payer receives the full credit even if they are not a participant.

---

# 4. Example — Equal Expense

Expense:

```text
Amount: ₹900
Paid by: Sidhant

Participants:
Sidhant ₹300
Rahul   ₹300
Arjun   ₹300
```

Balance effect:

```text
Sidhant +₹900 - ₹300 = +₹600
Rahul   -₹300
Arjun   -₹300
```

Final:

```text
Sidhant   +₹600
Rahul     -₹300
Arjun     -₹300
```

Sum:

```text
600 - 300 - 300 = 0
```

---

# 5. Payer Does Not Need to Participate

Example:

```text
Amount: ₹900
Paid by: Rahul

Participants:
Sidhant ₹450
Arjun   ₹450
```

Balance effect:

```text
Rahul   +₹900
Sidhant -₹450
Arjun   -₹450
```

Final:

```text
Rahul    +₹900
Sidhant  -₹450
Arjun    -₹450
```

---

# 6. One-Person Expense

An expense can contain exactly one participant.

Example:

```text
Amount: ₹500
Paid by: Sidhant
Participant: Sidhant ₹500
```

Balance effect:

```text
Sidhant +₹500 - ₹500 = ₹0
```

This is valid.

---

# 7. Equal Split Algorithm

When participants are selected without manually editing shares, divide the amount evenly using integer arithmetic.

Given:

```text
amount = A
participants = N
```

Calculate:

```text
base = floor(A / N)
remainder = A % N
```

Each participant initially receives:

```text
base
```

Then distribute one additional rupee to the first `remainder` participants in deterministic participant-selection order.

Example:

```text
₹100 / 3

base = 33
remainder = 1
```

Shares:

```text
Participant 1 → ₹34
Participant 2 → ₹33
Participant 3 → ₹33
```

Total:

```text
34 + 33 + 33 = ₹100
```

The result must always be deterministic.

---

# 8. Unequal Split Algorithm

When users manually edit individual shares:

```text
share.amount >= 0
```

and:

```text
sum(all shares) == expense.amount
```

The expense cannot be submitted otherwise.

No percentage-based split is required.

No decimal/paise amounts are supported.

---

# 9. Expense Validation

Every expense must satisfy:

```text
1 <= amount <= 99,999
```

Additionally:

- Description is required.
- Description cannot be whitespace-only.
- Description maximum = 150 characters.
- Payer must exist.
- Payer must belong to the group.
- Payer must be active at creation.
- At least one participant is required.
- Every participant must belong to the group.
- Every participant must be active at creation.
- Participants cannot be duplicated.
- Shares must be whole non-negative integers.
- Share total must exactly equal expense amount.
- Category, when supplied, must belong to the same group.

The backend is authoritative even if the frontend performs the same validation.

---

# 10. Expense Creation

Creating an expense consists of:

```text
Validate request
      ↓
Create expense
      ↓
Create expense shares
      ↓
Commit transaction
```

Expense and shares must be created atomically.

If any part fails:

```text
rollback everything
```

No partially created expense is allowed.

---

# 11. Expense Timestamp

The authoritative creation timestamp is generated by the backend/database.

The client must not be trusted to define the transaction timestamp.

Editing an expense does not change its original creation timestamp.

---

# 12. Expense Editing

Editing an expense changes the existing expense rather than creating a new one.

Conceptually:

```text
Old expense contribution
        ↓
Remove old contribution
        ↓
Apply new expense contribution
```

The database implementation should update the expense and its shares transactionally.

The expense:

- Keeps its original ID.
- Keeps its original creation timestamp.
- Gets new validated amount/payer/shares/etc.
- Causes balances to be recalculated.

---

# 13. Expense Deletion

Deleting an expense removes:

```text
expense
+
expense shares
```

The balance engine then calculates the new current balances from the remaining financial records.

Settlement records are not automatically edited or deleted.

---

# 14. Categories

Categories are metadata only.

They have no effect on:

- Expense amount
- Expense shares
- Balances
- Settlements
- Smart Settlement

Removing a category changes existing expenses referencing it to:

```text
category_id = NULL
```

They become Uncategorized.

---

# 15. Balance Calculation From Scratch

The preferred authoritative balance calculation is derived from persisted records.

Initialize:

```text
balance[person] = 0
```

for relevant group members.

For each expense:

```text
balance[payer] += expense.amount

for share in expense.shares:
    balance[share.person] -= share.amount
```

For each settlement:

```text
balance[from_person] += settlement.amount
balance[to_person] -= settlement.amount
```

After processing:

```text
sum(balance) == 0
```

This calculation should be centralized in a dedicated backend financial-logic module.

---

# 16. Why Balances Are Not Stored

Splitwise Pro does not maintain a separate balances table.

Balances are derived from:

```text
Expenses
+
Expense Shares
+
Settlements
+
Person-removal rules
```

This avoids having multiple mutable sources of truth.

---

# 17. Person Removal

Person removal is a soft removal.

The database record remains:

```text
is_active = false
```

Historical expenses remain intact.

The removed person cannot be selected for new expenses.

The current financial calculation applies the following removal rule.

---

# 18. Person Removal Financial Rule

When a person is removed:

### A. Amount the person owes the group

If the removed person has a net negative balance, that obligation is transferred to the remaining active group members.

Example:

```text
Rahul = -₹600
```

Rahul is removed.

The ₹600 obligation is redistributed among the remaining active people.

For deterministic MVP behavior, the redistribution is equal among the remaining active people, with integer-rupee remainder handling using the same deterministic ordering rule used elsewhere.

Example with:

```text
Sidhant
Arjun
Varun
```

Remaining members:

```text
Sidhant → -₹200
Arjun   → -₹200
Varun   → -₹200
```

The removed person's negative balance is therefore absorbed by the group.

---

# 19. Person Removal — Amount the Group Owes the Person

If the removed person has a positive balance, that receivable is removed from the group's current financial state.

Example:

```text
Rahul = +₹700
```

Rahul is removed.

The group's current balances no longer include the ₹700 owed to Rahul.

Historical transactions remain visible, but Rahul's receivable is no longer an outstanding group obligation.

---

# 20. Person Removal Example

Before removal:

```text
Sidhant   +₹300
Rahul     -₹600
Arjun     +₹300
```

Total:

```text
300 - 600 + 300 = 0
```

Remove Rahul.

Rahul owes the group:

```text
₹600
```

There are two remaining members.

Redistribute equally:

```text
Sidhant   -₹300
Arjun     -₹300
```

The removed person's negative obligation has been absorbed by the remaining members.

The historical transaction records are unchanged.

---

# 21. Person Removal With Positive Balance

Before removal:

```text
Sidhant   -₹300
Rahul     +₹600
Arjun     -₹300
```

Rahul is removed.

Rahul's ₹600 receivable is removed.

The remaining group members' current financial positions are recalculated according to the removal rule.

Historical records remain available for reference.

---

# 22. Person Removal Implementation Principle

Do not rewrite every historical expense when a person is removed.

Instead:

```text
Historical data
       ↓
Remain immutable
       ↓
Balance engine
       ↓
Apply active-member/removal adjustments
       ↓
Current balances
```

This preserves transaction history while allowing the current financial state to reflect the removal.

---

# 23. Important Removal Constraint

A removed person cannot be used in a newly created expense.

Existing historical expenses may continue to reference them.

A removed person may remain visible in transaction history so that historical records remain understandable.

---

# 24. Settlement Model

A settlement represents money physically paid between two people.

Example:

```text
Rahul → Sidhant ₹400
```

Financial effect:

```text
Rahul   += ₹400
Sidhant -= ₹400
```

Therefore a debtor moves toward zero and the creditor moves toward zero.

---

# 25. Settlement Validation

A settlement must satisfy:

```text
amount >= 1
from_person != to_person
```

Both people must belong to the same group.

The request must be authorized with the admin password.

The backend validates the settlement against the current financial state according to the application's settlement rules.

---

# 26. Settlement Immutability

Once created, a settlement is append-only.

There is no:

```text
PATCH settlement
DELETE settlement
UNDO settlement
```

endpoint.

If an incorrect settlement is recorded, the correction is represented by a new settlement.

---

# 27. Smart Settlement

Smart Settlement generates deterministic payment suggestions from current net balances.

It does not create or persist records.

Input:

```text
Current balances
```

Output:

```text
Suggested payments
```

---

# 28. Smart Settlement Algorithm

Separate balances into:

```text
Creditors = balance > 0
Debtors   = balance < 0
```

For example:

```text
A = +₹1000
B = +₹500
C = -₹700
D = -₹800
```

Create:

```text
Creditors:
A → ₹1000
B → ₹500

Debtors:
C → ₹700
D → ₹800
```

Then match them deterministically.

---

# 29. Creditor/Debtor Matching

Take the first debtor and first creditor.

Calculate:

```text
payment = min(debtor_remaining, creditor_remaining)
```

Create:

```text
debtor → creditor = payment
```

Subtract payment from both.

When one reaches zero, move to the next.

Repeat until all balances reach zero.

---

# 30. Smart Settlement Example

Starting balances:

```text
A +₹1000
B +₹500
C -₹700
D -₹800
```

Suggestions:

```text
C → A ₹700
D → A ₹300
D → B ₹500
```

After these payments:

```text
A = ₹0
B = ₹0
C = ₹0
D = ₹0
```

---

# 31. Smart Settlement Rules

Suggestions must:

- Use current balances.
- Never contain zero amounts.
- Never contain negative amounts.
- Never contain self-payments.
- Preserve the total net balance.
- Fully settle all current positive/negative balances when possible.
- Be deterministic for the same input state.

Smart settlement suggestions are not stored.

---

# 32. Settlement After Smart Settlement

The Smart Settlement screen may display multiple suggestions.

Each suggestion has its own:

```text
✓ Log Settlement
```

button.

When one is logged:

```text
Suggestion
    ↓
Create settlement
    ↓
Current balances change
    ↓
Recalculate remaining suggestions
```

The UI must not assume all previously displayed suggestions are still valid after one settlement is logged.

---

# 33. Settlement History and Balances

Settlement history is financial input to the balance engine.

For:

```text
Rahul → Sidhant ₹400
```

the balance calculation includes:

```text
Rahul   +₹400
Sidhant -₹400
```

Therefore logged settlements automatically reduce outstanding balances.

---

# 34. Editing an Expense After Settlement

Settlements are independent immutable records.

If an expense is edited after a settlement:

```text
Updated expense
        +
Existing settlements
        ↓
Recalculate current balances
```

The settlement itself is not rewritten.

This may produce a new outstanding balance, which can then be handled through new settlements.

---

# 35. Deleting an Expense After Settlement

Deleting an expense:

```text
Remove expense
Remove shares
Keep settlements
Recalculate balances
```

The system must not automatically reverse or delete a settlement.

---

# 36. Multiple Simultaneous Expenses

Multiple clients can create expenses at the same time.

Example:

```text
Client A → Expense A
Client B → Expense B
```

Both should succeed if independently valid.

Use:

- UUID IDs
- Database transactions
- No global application lock

After persistence, the balance engine derives the current state from all committed records.

---

# 37. Timestamp Ordering

Transactions are ordered primarily by:

```text
created_at DESC
```

If two records have identical timestamps, use a deterministic secondary ordering such as UUID.

The exact tie-breaker does not affect financial calculations.

---

# 38. Financial Integer Rules

All monetary values are integers.

Valid:

```text
₹1
₹100
₹99999
```

Invalid:

```text
₹100.50
₹0
-₹100
```

No floating-point arithmetic should be used for money.

Use integer arithmetic throughout the backend.

---

# 39. Balance Invariant

After every successful financial mutation:

```text
sum(current balances) == 0
```

This should be asserted in automated tests.

A violation indicates a financial-logic bug.

---

# 40. Transaction Atomicity

The following operations must be atomic:

### Create expense

```text
Expense + Shares
```

### Update expense

```text
Expense update + Share replacement
```

### Delete expense

```text
Expense + Shares
```

### Log settlement

```text
Settlement record
```

### Delete category

```text
Category references → NULL
+
Category deletion
```

### Delete group

```text
All dependent records
+
Group deletion
```

If any required step fails, the entire mutation must roll back.

---

# 41. Clear Transactions

The clear-transactions operation is destructive and password-protected.

The exact set of records deleted must match the final product rule.

Recommended complete-reset interpretation:

```text
Expenses
+
Expense Shares
+
Settlement History
```

are cleared.

People and categories remain.

The operation must be atomic.

---

# 42. Group Deletion

Deleting a group removes the entire group and its dependent data.

Conceptually:

```text
Group
 ├── People
 ├── Categories
 ├── Expenses
 │    └── Shares
 └── Settlements
```

The operation must be atomic.

---

# 43. No Client-Side Financial Authority

The frontend may calculate temporary UI values for responsiveness.

However:

```text
Frontend balance ≠ authoritative balance
```

The backend/database state is authoritative.

The client must never be trusted to submit:

- Final balances
- Settlement calculations
- Financial adjustments
- Historical timestamps

The backend recalculates or validates all important financial state.

---

# 44. Edge Cases

## ₹1 Expense

Valid:

```text
Amount = ₹1
```

---

## ₹100 / 3

Valid deterministic split:

```text
₹34
₹33
₹33
```

---

## Payer Not Included

Valid.

The payer receives the full credit while participants receive their shares as obligations.

---

## One Participant

Valid.

---

## Unequal Shares

Valid if:

```text
sum(shares) = amount
```

---

## Zero Share

A selected participant with a zero share should not normally be persisted as an actual participant share.

If a participant owes ₹0, the UI should generally leave them unselected.

Backend may reject or normalize zero-value participant shares according to implementation, but the core financial rule remains unchanged.

---

## No Outstanding Balance

If every current balance is zero:

```text
Outstanding

All settled 🎉
```

Smart Settlement returns:

```text
suggestions = []
```

---

## Multiple Creditors

Match deterministically in the chosen ordering.

---

## Multiple Debtors

Match deterministically in the chosen ordering.

---

## Exact Settlement

If a settlement brings a balance to zero, it should display as settled.

---

## Over-Settlement

The backend should prevent a settlement from creating an invalid financial state according to the settlement validation rules.

Do not allow arbitrary client-side manipulation of balances.

---

# 45. Determinism Requirements

The same database state must produce the same:

- Balances
- Equal split allocation
- Smart settlement suggestions
- Person-removal redistribution

Determinism makes the application easier to test and debug.

---

# 46. Algorithmic Complexity

Balance calculation:

```text
O(E + S)
```

where:

- `E` = number of expense records/shares processed
- `S` = number of settlements

Smart Settlement:

```text
O(P)
```

for standard creditor/debtor matching once balances are available, where:

- `P` = number of people involved in the settlement calculation

The group sizes expected for MVP are small, so simplicity is preferred over premature optimization.

# 50. Final Financial Principle

Splitwise Pro should always derive the current financial state from the underlying records and explicit business rules.

The fundamental pipeline is:

```text
Expenses
   +
Expense Shares
   +
Settlements
   +
Person-Removal Rules
        ↓
Balance Engine
        ↓
Current Net Balances
        ↓
Smart Settlement
        ↓
Suggested Payments
```

All calculations must be deterministic, integer-based, server-authoritative, and covered by automated tests.
